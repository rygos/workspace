# Security Requirements

Treat LLM output and AI-generated code as untrusted input.

Use explicit permissions for filesystem, network, clipboard, notifications, database, process execution and other sensitive capabilities. The agent also has scoped tool permissions. Avoid unrestricted shell access. Validate tool arguments and paths and prevent traversal outside allowed project/staging areas.

Dependencies introduced by the agent must be visible and policy checked. Avoid unnecessary dependencies. Never send project data to cloud AI implicitly; LM Studio/local OpenAI-compatible provider is the default.

Protect secrets from logs, LLM context, diffs and generated code. Redact credentials. Keep audit records of agent actions without storing hidden reasoning.

The repository tools are read-only and exist only in the native app. The user must select the project folder through the native folder picker. Native commands canonicalize that root, reject absolute and traversal paths, skip symlinks and common dependency/build directories, and accept only bounded text/source files. The project inventory exposes paths and extension counts without file contents, capped at 200 entries. Search caps file count, bytes scanned and result count; file reads cap file size and returned characters. The tools are not offered when the configured model host is not a loopback address.

Feature contracts and plans are validated structured data stored locally, with a cap of 30 drafts. Planned file paths must be relative and may not traverse parents. These records are proposals only: storing a plan does not approve or execute the described changes. Plan tools are offered only to a loopback model endpoint.

Staging snapshots are stored under the canonical application data directory, never in the selected source tree. Creating, each file edit and removing a snapshot require an in-app confirmation. An edit targets only a complete staging copy, accepts bounded text source paths with existing parent folders, rejects symlinks, secret files, ignored directories and the reserved metadata name, and caps content at 256 KiB. Replacements require the supplied old text to occur exactly once; creating a file requires it not to exist. A bounded file-level diff compares the copy with its recorded source only when that same source folder is selected. A snapshot skips symlinks, common build/dependency directories, recognized credential files, and the reserved Workshop metadata name; it is limited to 20,000 entries, 16 MiB per file, 100 MiB per copy and five retained copies. Partial copies are removed when copying fails; a crash leaves a marked incomplete entry that can be listed and removed after confirmation. Snapshots are copies, not Git worktrees, and do not include `.git` history.

The agent can create the fixed staging preview artifacts together in a complete copy after one direct confirmation showing plugin identity, declared permissions, entrypoint size and that preview code will later execute. This native command enforces the manifest and entrypoint size limits, restricts the entrypoint to `plugin.js`, accepts only no permission or `storage`, checks the same selected source root and refuses to overwrite existing files. It writes the entrypoint first and the manifest last so a visible manifest marks a completed artifact pair.

The local agent can read only the preview lifecycle state and plugin identity through a status tool; it cannot retrieve the staged source through that tool. Uncaught frame errors and unhandled promise rejections stop the preview frame and update its state. Closing Settings stops an active preview and its in-memory storage.

Starting a staging preview through the agent requires an explicit user request and a separate in-app confirmation naming the plugin and its permissions. Only after confirmation does the renderer load the fixed artifact pair and execute it in the sandbox; the tool returns the observed lifecycle state, not an activation result.

Static plugin validation reads only the fixed artifact pair from the selected source's complete staging copy and reports schema, permission, size and export-contract results without executing plugin code. A passing static report does not establish JavaScript syntax or runtime correctness; those are observed only by the separately confirmed sandbox preview.

Regular staged-plugin activation requires static checks and direct confirmation. It runs in the same opaque-origin sandbox, persists only the declared storage facade in that plugin's namespace, and does not auto-activate on app restart. An optional installation copies the validated manifest and bounded entrypoint into the local application store after direct confirmation; this catalog is stored outside plugin namespaces, holds at most five plugins and is limited to 2 MiB. Activating an installed artifact repeats validation and requires a new direct confirmation. Hot Reload keeps the old frame mounted until the candidate reports successful startup, then observes the new version for 10 seconds. Candidate storage changes are buffered and rolled back if loading fails. A runtime failure during the observation window stops the candidate, rolls back its storage changes and attempts to reload the previous version. Recovery snapshots are limited to 128 keys and 1 MiB per active version and are released after the observation window succeeds.

The lifecycle circuit breaker uses a persisted threshold of two to ten matching failures and a five-minute to two-hour window; defaults are three failures in 30 minutes. It applies to trusted and staged plugins. Quarantine blocks activation and canary repair. A direct confirmation is required before manually activating a quarantined staged plugin; repair tools cannot remove quarantine.

New trusted-plugin incidents and active staged-plugin runtime failures start an automatic diagnosis only when a loopback model server and model are configured. Trusted-plugin requests contain the incident ID, plugin ID/version, error type, severity, at most twelve stack frames (4 KiB total), at most five matching runtime log entries (240 characters each, with common bearer/API-key patterns redacted) and the registered plugin's activation function capped at 4 KiB after credential redaction. Staged-plugin requests add only the active `plugin.js` entrypoint, capped at 4 KiB after credential redaction. Source is passed in memory and is not persisted. The original exception message is omitted from stack context. The diagnosis summary is capped at 1,600 characters and stored in the local incident journal. Stack frames, source and diagnosis text stay out of `inspect_incidents`; only the loopback-only Repair Agent receives them. Source content is treated as untrusted evidence and the diagnostic request has no agent tools, cannot edit code and cannot activate plugins.

After a staged-plugin diagnosis, the repair agent may request at most one exact text replacement in `plugin.js` of the stage copy that supplied the failed runtime per attempt. The model receives no general agent tools: its repair bridge exposes only that replacement, a static artifact check, the fixed test gate and the canary action. Workshop displays the full replacement and requires direct confirmation before editing. The edit cannot target the selected source tree, the manifest, or an active runtime artifact. After static checks pass, Workshop asks separately before `bun test`; project scripts may access local files and the network. After tests pass, Workshop asks again before canary activation, revalidates the stage and version and observes the isolated runtime for ten seconds. Below the circuit breaker threshold, same-plugin Hot Reload restores the prior frame when available; when the breaker opens, the runtime remains stopped. Settings allow zero to three automatic attempts per plugin in an app session, defaulting to one. The configurable matching-failure threshold and time window apply to staged runtime failures as well as trusted plugins. Quarantine can be cleared only through a separately confirmed manual activation. Failed and cancelled canaries are recorded.

Validation runs only the fixed Bun build, check or test gates in a complete staging copy and requires its own confirmation. The Bun process receives a reduced environment, output is capped and common bearer/API key patterns are redacted, and the process tree is terminated after 120 seconds. Project scripts remain executable code with access to the user's local files and network; the confirmation dialog states this limitation. No arbitrary executable or argument tool is exposed.

The agent may activate only a plugin already accepted by the build-registered plugin loader, after showing its declared permissions and receiving direct confirmation. Staging source is never imported into Workshop's trusted plugin host. Settings can preview or activate the fixed artifact pair `workshop-plugin.json` + `plugin.js` from the selected source's complete staging copy after direct confirmation. The native command reads only these fixed paths, rejects symlinks and caps the manifest at 16 KiB and entrypoint at 256 KiB. The renderer validates the manifest and requires the entrypoint to be bundled as `plugin.js`. The iframe uses `sandbox="allow-scripts"`, no same-origin access, no network, no top-level navigation and no parent DOM access. Its bridge accepts only bounded storage operations when the manifest declares the storage permission. Preview storage is in-memory, limited to 128 keys and 1 MiB, and discarded on close. Regular staged activation uses the plugin's persistent namespaced storage but is session-scoped and not resumed after restart. The sandbox does not impose CPU or memory quotas on arbitrary plugin code. Staged runtime code remains distinct from build-registered plugins.
