# Roadmap

The current increment completes the app shell, browser-preview connectivity and offline behavior, and adds bounded development tools. The OpenAI-compatible client has model-discovery, streaming and structured tool-call tests against a local mock server. Browser chat and a read-only `list_plugins` tool round trip were manually verified against the configured LM Studio endpoint; the native Tauri UI path still needs its own interaction smoke verification. A bounded project inventory, repository search and file reader are available in the native app after the user selects a folder, and are exposed only for loopback model endpoints. The agent can prepare changes in a separately confirmed staging copy and cannot modify the selected project source directly. The native Settings screen can load, validate, preview and activate the documented `workshop-plugin.json` + `plugin.js` artifact from the selected project's staging copy in an isolated iframe runtime. Accepted artifacts can be installed persistently in local application data, but activation remains explicit and session-scoped; trusted host plugins remain build-registered.

Automatic diagnosis for new trusted-plugin incidents and active staged-plugin runtime failures includes bounded source context when available. Trusted-plugin diagnosis sends only the registered plugin's activation function, capped at 4 KiB, plus the incident identity, version, up to twelve bounded stack frames and up to five redacted runtime log entries. Staged-plugin diagnosis adds only its redacted `plugin.js` entrypoint, capped at 4 KiB. Source is passed transiently in memory to loopback models; both flows store only a capped diagnosis summary in incident history. Stack frames and source are not exposed through the general incident tool. A staged-plugin incident can also request one exact `plugin.js` replacement in its staging copy, with direct confirmation and static artifact validation; it never activates the repair. Regression validation and the remaining repair state machine are still open.

## Phase 0 — Design
Architecture, threat model, plugin contract, error containment model, ADRs. (Documented.)

## Phase 1 — Shell
Tauri 2 shell, empty workspace, persistent right chat rail, settings, resizer, command palette, offline retry, local settings/chat persistence, and a bounded in-memory structured log. (Implemented; native build starts.)

## Phase 2 — AI Provider
Generic OpenAI-compatible client with LM Studio defaults, model discovery, API key session handling, cancellable SSE chat, and graceful offline behavior. The browser-only Vite preview buffers its streaming request body before forwarding to the fixed loopback proxy. (Implemented; provider unit/integration tests use a local mock. Browser chat was manually verified against LM Studio; native Tauri smoke remains pending.)

## Phase 3 — Extension Runtime
Plugin manifest validation, lifecycle host, permission-checked SDK facades, Event Bus, typed Capability Registry, namespaced storage API, and a demo notes service are implemented and tested. Startup discovers a validated build-registered module; Settings can activate/deactivate it and expose the notes workspace contribution with create, edit, delete and persistence. External module discovery, generic plugin UI contributions, and generated module support remain open.

## Phase 4 — Reliability
Core failures are recorded locally without storing exception messages, and Settings shows incidents and safe-mode state. The lifecycle supervisor bounds repeated plugin activation/event failures, quarantines on the configured threshold, records an explicitly observed Last Known Good version and restores it through the plugin host. The plugin manager exposes these lifecycle actions; activation rollback and recovery are covered by tests. Staged replacement and its canary recovery are implemented in Phase 6; broader trusted-plugin replacement and automatic UI recovery remain open.

## Phase 5 — Development Agent
The bounded tool layer can list plugins, inspect capability dependencies and incidents, and read up to 25 recent structured logs. In the native app, the user can explicitly select a project folder for a capped machine-readable file/directory inventory, bounded text search and source/document reading. The agent can validate, store locally and retrieve up to 30 structured feature-contract drafts containing requirements, capabilities, permissions, persistence needs, acceptance criteria, proposed files, validation steps and risks. Core changes require a rationale; capability and persistence requirements must match declared plugin permissions. These drafts do not authorize implementation. After an explicit request and confirmation, the user can create a bounded snapshot copy under app data; the source remains unchanged, common dependency/build and secret files are excluded, and only five copies of at most 100 MiB each are retained. Listing and confirmed removal are supported. Each staging edit requires another direct confirmation and can only add a text source file or replace an exact, unique text span in a complete copy, up to 256 KiB. A bounded file-level diff compares the copy with its recorded source while that same folder is selected. After direct confirmation, the native agent can run only the fixed `bun run build`, `bun run check` and `bun test` gates in that staging copy, with a 120-second timeout and capped/redacted output; project scripts can still access local files and network. The agent can also activate an already build-registered plugin after direct confirmation. A storage-only staging artifact can be statically checked and separately previewed or activated in a sandboxed iframe; preview storage is temporary, while regular activation uses a namespaced persistent plugin store. Staged runtime code remains separate from the trusted plugin host and does not auto-activate after restart. Repository, plan and staging tools are exposed only to loopback model endpoints. Tool arguments are validated, log secrets are redacted, calls are limited to three rounds/six actions, and no free-form command interface is exposed.

## Phase 6 — Self-extension
Natural-language feature -> generated TypeScript plugin -> tests -> activation -> hot reload. The first staging artifact contract and isolated preview are implemented for bundled, storage-only plugins. The user can statically validate a staging artifact, activate it in the main workspace after direct confirmation, hot reload a changed artifact with the same plugin ID, or install an accepted artifact in the local app catalog. Installations retain the bounded manifest and entrypoint after the staging copy is removed; each activation revalidates the saved artifact and requires fresh direct confirmation, and no staged code runs automatically at startup. The runtime uses an opaque-origin sandbox with namespaced storage; a failed hot reload keeps the previous frame and rolls back candidate writes. Uncaught active-plugin errors stop the frame; errors during the 10-second activation observation window restore the previous storage snapshot and reload the previous version after Hot Reload. Storage recovery is bounded to 128 keys and 1 MiB. Trusted host plugins remain build-registered.

## Phase 7 — Repair Agent
Automatic diagnosis is implemented for new trusted-plugin incidents and active staged-plugin runtime failures. Trusted-plugin activation code and staged-plugin entrypoint source are bounded, redacted and transient, and are passed only to loopback diagnosis. A staged-plugin failure can produce at most one exact replacement in the associated staging copy; Workshop requires direct confirmation, then runs only the static plugin acceptance checks. The candidate is left staged and is never activated automatically. Remaining: regression validation, canary activation, observation, configurable retry budget, circuit breaker integration and quarantine/rollback orchestration.

## Phase 8 — Hardening
Dependency graph regression analysis, permissions, migration safety, export/backups, E2E tests and packaging for Linux/Windows/macOS.
